> 如果要你提出具体的优化建议，分为功能层面和交互层面（或者说UI层面），你会提什么建议？详细说明

从当前项目状态看，我不会先建议增加「批量 URL」「公网粘贴链接」「复杂多 Agent」这类扩展功能。当前真正影响产品可用性的不是功能数量，而是三件事：

1. 采集是否能明确证明“抓全了”。
2. 中途失败后能否从已有数据继续，而不是重新采集。
3. 用户是否能看懂当前任务处于什么状态，以及失败后该怎么恢复。

因此我会把优化分为“数据和流程可靠性”“报告能力”“工作台交互”三个优先级来做。

**一、功能层面**

### P0：先解决评论完整性和数据可信度

这是最重要的一项。

当前 [extension/src/shared/api/zhihu-api.ts](./extension/src/shared/api/zhihu-api.ts) 会分别拉取一级评论和子评论，但最终的完整性判断仍然比较粗：

- `paging.totals` 的含义并不稳定，不能始终直接当作总评论数。
- `content.commentCount` 有时为空。
- `fetchAllComments()` 遇到部分 403 时会抛出错误，但已经拉到的部分评论不会顺利进入下一步报告流程。
- [extension/src/shared/converters/json-export.ts](./extension/src/shared/converters/json-export.ts) 目前主要检查一级评论的子评论数量，递归子节点的缺口还可以继续加强。
- 当前样例里可以看到“56 个一级评论、97 个总节点、最大深度 2”，这几个数字应该在产品中明确区分，而不是只显示一个“97 条评论”。

建议把完整性模型改成显式的多维统计，而不是单一的 `capture_ratio`：

```json
{
  "completeness": {
    "status": "complete",
    "expected_root_count": 56,
    "captured_root_count": 56,
    "expected_total_count": null,
    "captured_total_count": 97,
    "root_pages": 3,
    "child_requests": 56,
    "child_completed": 54,
    "child_failed_ids": [],
    "pagination_finished": true,
    "source": "comment_v5",
    "warnings": []
  }
}
```

这里不一定要直接使用这些字段名，但概念应该分开：

- 一级评论预期数量。
- 一级评论实际数量。
- 所有节点实际数量。
- 已请求的楼中楼数量。
- 成功获取的楼中楼数量。
- 失败的评论 ID。
- 分页是否正常结束。
- 数量来源是什么。
- 当前数据状态是完整、部分完整，还是未知。

需要特别避免这种情况：

```text
页面显示 56 条评论
系统抓到 97 个节点
最终界面显示“97 / 56，抓取率 100%”
```

这会让用户无法判断系统到底是抓多了、抓全了，还是统计口径错了。

建议增加三个采集状态：

```text
完整：分页结束，所有声明的子评论均已处理
部分完成：有评论或楼中楼请求失败，但已保存已有数据
未知：知乎没有返回可靠的总数，系统只能报告实际抓到的数量
```

验收标准：

- 97 节点的样例能明确显示“一级 56，全部节点 97”。
- 任何一个子评论请求失败，报告上方必须出现“部分完成”，不能显示为完全成功。
- 403 发生后，用户可以保存已经采集的部分 bundle。
- bundle 中能找到具体失败的评论 ID，而不是只有一条笼统的错误文字。

### P0：把采集、分析、渲染拆成可恢复的阶段

当前 [extension/src/shared/analysis/runReport.ts](./extension/src/shared/analysis/runReport.ts) 每次“重新生成”基本都会重新走：

```text
采集评论
→ 写 bundle
→ 调模型
→ 生成 HTML
```

这在第一次运行时没问题，但后续会产生几个问题：

- 模型调用失败，用户不得不重新采集评论。
- HTML 渲染有问题，也会重新消耗采集时间。
- 工作台标签页意外关闭后，任务状态可能丢失。
- `takePendingTask()` 会在读取待办时立即删除任务，任务尚未成功开始就可能消失。
- 现在 Python 有 `--html-only`，但扩展工作台没有对应的“仅重新分析”和“仅重新渲染”能力。

建议把任务拆成独立可重跑的阶段：

```text
任务创建
  ├── 采集
  ├── 保存 bundle
  ├── 分析 bundle
  ├── 保存 llm_raw
  └── 渲染 report
```

每个阶段都保存状态：

```json
{
  "task_id": "t_xxx",
  "status": "analyzing",
  "source_url": "...",
  "bundle_path": "...",
  "raw_result_path": null,
  "report_path": null,
  "last_error": null,
  "updated_at": "..."
}
```

工作台至少提供三个操作：

- `重新采集并分析`
- `仅重新分析已有 bundle`
- `仅重新生成 HTML`

其中“仅重新分析”应该成为近期最值得实现的功能。它可以显著减少调试提示词、调试报告样式时的时间和 API 消耗。

Python 端可以保留现有：

```powershell
python run.py xxx.bundle.json --html-only
```

扩展端也应该拥有等价流程。

验收标准：

- LLM 失败后，重新点击分析不会再次请求知乎评论。
- HTML 报告样式修改后，可以直接用 `llm_raw.json` 重渲染。
- 关闭工作台再打开，可以看到最近任务和失败原因。
- 任务不会因为工作台初始化阶段读取一次就永久丢失。

### P0：给模型输出增加结构校验

当前 [extension/src/shared/analysis/llm.ts](./extension/src/shared/analysis/llm.ts) 和 [analyze/llm.py](./analyze/llm.py) 主要做两件事：

1. 解析 JSON。
2. 把 JSON 直接交给报告渲染。

这还不够。模型可能返回合法 JSON，但内容不符合系统要求，例如：

- `stance` 缺少字段。
- 三种态度比例不在 0 到 100 之间。
- 百分比加起来不是约 100。
- `topic_tree` 没有根节点。
- `quote_ids` 引用了不存在的评论 ID。
- 一级议题超过几十个，报告无法阅读。
- `highlights` 的 `likes` 是字符串或者不存在。
- `report_markdown` 为空，但系统仍显示“完成”。

建议在报告生成前增加 `validateAnalysisResult()`：

```text
检查结果是否为对象
检查 answer_summary 是否存在
检查 stance.support / oppose / neutral 是否为数字
检查百分比范围和总和
检查 topic_tree 根节点是否存在
检查 topic_tree 总节点数和最大深度
检查 quote_ids 是否来自 bundle
检查 highlights 的 comment_id 是否真实存在
```

错误处理应分三级：

```text
轻微问题：自动修正，例如数字字符串转数字
可修复问题：发送一次“请修复 JSON”请求
严重问题：不生成“成功报告”，提示用户重试
```

报告里还应该保存分析元数据：

```json
{
  "analysis_meta": {
    "model": "deepseek-chat",
    "prompt_version": "2026-10-03",
    "input_comment_count": 97,
    "input_chars": 18500,
    "created_at": "...",
    "validation_warnings": []
  }
}
```

这样未来才能知道某份报告是用什么模型、什么提示词、什么数据生成的。

### P0：统一扩展和 Python 的数据、提示词与报告契约

目前有两套相似但独立的实现：

- 扩展侧：[extension/src/shared/analysis/prompts.ts](./extension/src/shared/analysis/prompts.ts)
- Python 侧：[analyze/prompts.py](./analyze/prompts.py) 和 [configs/prompts.json](./configs/prompts.json)
- 扩展侧 HTML：[extension/src/shared/analysis/htmlReport.ts](./extension/src/shared/analysis/htmlReport.ts)
- Python 侧 HTML：[analyze/html_report.py](./analyze/html_report.py)

目前两边的提示词虽然目标一致，但并不是严格的单一来源。长期会出现：

```text
扩展跑出来的议题树和 Python 跑出来的不一样
扩展支持某个字段，Python 不支持
Python 报告修了一个问题，扩展报告没有同步
```

建议建立一个明确的契约：

```text
bundle schema v1
analysis result schema v1
prompt preset v1
report renderer input schema v1
```

比较务实的做法是：

- 用仓库根目录的 JSON 文件作为默认提示词单一来源。
- Python 直接读取这个文件。
- 扩展构建时把该文件复制或打包进扩展。
- 用户在扩展内修改后，保存为本地覆盖配置。
- 提供提示词导出/导入，而不是让两套配置永久独立。

报告渲染可以先不强行共用代码，但两边必须共用同一份分析 JSON 结构。

### P1：改进回答正文和元数据提取

交接文档已经记录了 `voteup_count` / `comment_count` 经常为空。当前 [extension/src/content/detector.ts](./extension/src/content/detector.ts) 对回答主要依赖：

```text
initialData.entities.answers[id]
```

然后再用 DOM 补正文。

建议把回答元数据提取做成多来源合并，而不是简单的“initialData 或 DOM 二选一”：

```text
initialData
→ 页面 DOM 属性和按钮文本
→ 回答容器上的 data-* 属性
→ 回答 API 或页面已有的结构化数据
→ 最终为空
```

并且为每个字段记录来源：

```json
{
  "voteup_count": {
    "value": 128,
    "source": "initialData"
  },
  "comment_count": {
    "value": 56,
    "source": "dom"
  }
}
```

这样以后遇到知乎页面结构变化时，能知道是哪一种来源失效，而不是只看到最终字段是 `null`。

建议补充固定 fixture 测试：

- 完整 initialData。
- initialData 缺少赞数，但 DOM 有。
- DOM 内容比 initialData 长。
- 初始数据结构变化。
- 问题页和回答页混淆。
- 作者名称含特殊字符。
- 回答正文为空但评论仍可采集。

### P1：增强大评论量的分析策略

当前 [extension/src/shared/analysis/corpus.ts](./extension/src/shared/analysis/corpus.ts) 会把所有评论都放入语料，只对单条评论做字符截断。

对于几十条、几百条评论可以工作，但评论数量继续增长后会遇到：

- 输入 token 超限。
- 高赞评论占据主要上下文，低赞但重要的反对观点被忽略。
- 长评论被简单截断，可能失去关键结论。
- 用户不知道哪些评论被送入模型，哪些被省略。

建议引入可解释的压缩策略：

```text
完整保存原始评论
→ 高赞评论全部保留
→ 各态度/时间段抽样
→ 长评论先摘要再进入总分析
→ 记录输入评论数和省略数量
```

报告上显示：

```text
原始评论：937 条
本次分析使用：312 条
完整保留：高赞 100 条、反对观点 84 条、随机覆盖 128 条
```

不要只在后台静默截断，否则用户会误以为模型看到了所有原文。

### P1：建立任务历史和结果管理

现在系统基本是“当前任务工作台”，缺少历史任务视图。建议在用户选择的临时目录中维护一个轻量任务索引，或者使用 `chrome.storage.local` 保存最近任务元数据：

```text
任务标题
回答作者
原回答 URL
采集时间
评论数量
任务状态
bundle 路径
报告路径
错误信息
模型名称
```

历史页不必很复杂，列表就够：

```text
标题 | 作者 | 评论数 | 状态 | 更新时间 | 操作
```

操作包括：

- 查看报告。
- 仅重新分析。
- 重新生成 HTML。
- 打开原回答。
- 删除本地数据。
- 导出 bundle。

这会比单纯增加“批量 URL”更能提升日常使用效率。

### P1：增加可控的隐私和数据保留功能

bundle 中包含：

- 评论正文。
- 作者 ID。
- `url_token`。
- IP 属地。
- 回复关系。
- 原始回答 URL。

当前交接文档已经明确这是个人学习研究用途，但产品最好把隐私边界做成实际选项：

- 是否保存作者 ID 和 `url_token`。
- 是否保存 IP 属地。
- 是否只保留分析所需字段。
- 是否在报告中显示原评论 ID。
- 一键删除某个任务的全部本地文件。
- API Key 存储状态提示。
- 日志中禁止输出 API Key 和完整评论正文。

可以提供两个模式：

```text
完整归档：保留富字段 bundle
分析最小化：仅保存正文、点赞、层级和必要作者名称
```

这比在文档中单独提醒“不要外传”更可靠。

**二、交互和 UI 层面**

### P0：重新设计工作台的任务状态，而不是继续堆卡片

当前 [extension/src/workbench/WorkbenchApp.tsx](./extension/src/workbench/WorkbenchApp.tsx) 已经有侧边步骤、日志和报告 iframe，这是一个合理基础，但目前存在几个交互问题：

- 工作台没有任务历史。
- 没有 bundle 重新分析入口。
- “重新生成”这个按钮不明确是否会重新采集。
- 进度百分比比较抽象。
- 失败后主要依靠日志文本恢复。
- 设置、提示词、API Key 都放在侧边卡片里，任务运行时容易挤压主内容。
- 页面没有清楚区分“采集成功”和“分析成功”。

建议把工作台拆成四种明确状态：

```text
空闲 / 等待任务
首次配置
任务执行中
报告完成或任务失败
```

页面顶部固定显示：

```text
当前任务标题
答主
原回答链接
任务状态
数据保存目录
```

主区域则根据状态变化：

```text
空闲：新建报告、选择 bundle、查看历史
配置：API 和本地目录检查
执行：阶段进度与可恢复操作
完成：报告概览和后续操作
失败：错误原因和恢复按钮
```

### P0：把采集进度从“百分比”改成可解释指标

当前页面显示“10%、45%、88%”等进度，但用户不知道这个比例代表什么。

采集阶段应该显示：

```text
一级评论：56 / 56
楼中楼任务：54 / 56
已抓取节点：97
失败请求：0
分页状态：已结束
```

模型阶段应该显示：

```text
输入评论：97 条
输入字符：18,420
模型：deepseek-chat
请求状态：等待 / 生成中 / 校验中
```

报告阶段应该显示：

```text
议题树节点：14
典型原话：8
报告文件：xxx.report.html
```

这样用户能判断系统是不是卡住，也能判断最终结果是否可信。

### P0：为每类错误提供对应的恢复动作

现在 `WorkbenchApp` 主要把错误写进日志和红色提示中，但“错误文字”不等于“错误处理”。

建议建立错误类型和动作映射：

| 错误           | 用户能看到的解释           | 直接操作                       |
| -------------- | -------------------------- | ------------------------------ |
| 403 / 验证码   | 知乎暂时限制了请求         | 返回知乎页、完成验证、重新采集 |
| 没有知乎标签页 | 工作台找不到用于签名的页面 | 打开/刷新知乎回答页            |
| 文件夹权限失效 | 浏览器失去了目录写权限     | 重新选择目录                   |
| LLM 401        | API Key 无效               | 打开设置并重新保存             |
| LLM 429        | 模型限流                   | 等待后重试                     |
| JSON 校验失败  | 模型返回结构不符合报告要求 | 自动修复一次或重新分析         |
| 子评论部分失败 | 有部分评论没有拉到         | 保存部分 bundle、重试失败项    |

失败面板中至少显示：

```text
发生在哪个阶段
错误类型
已经保存了什么
是否会再次调用知乎
推荐的下一步
```

例如：

```text
模型分析失败

评论已成功保存为 bundle。
不会重新采集评论。
你可以：
[仅重新分析] [修改提示词后重试] [查看 bundle]
```

这会比让用户重新点击“重新生成”清楚得多。

### P1：首次配置流程应该是“检查清单”

当前首次配置页直接展示 API Key、Base URL、模型、目录四个输入项。建议改成明确的设置步骤：

```text
1. 选择模型服务
2. 填写 API Key
3. 测试连接
4. 选择数据目录
5. 检查知乎页面连接
6. 开始任务
```

每一步都应有状态：

```text
未设置
已设置
测试成功
需要重新授权
```

具体建议：

- Base URL 提供 DeepSeek 默认值。
- 模型提供默认值，同时允许手动输入。
- API Key 增加显示/隐藏按钮。
- 增加“测试 API”按钮，只发送最小请求。
- 选择目录后显示目录名称和权限状态。
- 说明 bundle 和报告会写入本地目录。
- 不要让用户在输入完成后才发现目录权限无效。
- 配置未保存时，离开页面前提醒。

### P1：提示词编辑不适合长期放在侧边栏

当前提示词编辑区位于左侧卡片，两个大文本框会明显拉长侧栏。建议改成独立设置抽屉或模态页面：

```text
设置
├── 模型连接
├── 提示词
│   ├── System
│   ├── User 模板
│   ├── 变量检查
│   ├── 恢复默认
│   ├── 导入
│   └── 导出
└── 数据与隐私
```

提示词页面应该提供：

- `{validation}` 和 `{corpus}` 是否存在的实时检查。
- 当前提示词版本。
- 最近修改时间。
- 恢复默认。
- 导出提示词配置。
- 使用样例 bundle 预览实际发送给模型的内容。
- 显示预计输入字符数。
- 运行任务时锁定编辑，避免任务使用的提示词和界面当前内容不一致。

“设置 / 提示词”这个入口可以保留，但不要让完整编辑器长期占据任务主视图。

### P1：报告预览应当从 iframe 升级为真正的报告阅读界面

当前 iframe 预览可以工作，但用户只能看到一整张 HTML 页面，报告和工作台的关系比较松散。

建议至少增加以下能力：

- 报告顶部固定显示回答标题、答主、评论数、采集状态和生成时间。
- 报告内部提供目录：
  - 答主摘要
  - 议题树
  - 态度估算
  - 争议点
  - 典型原话
  - 完整报告
- 议题树支持展开全部、收起全部。
- 按支持、反对、中立、混合筛选节点。
- 按关键词搜索议题。
- 点击 `quote_id` 可以定位到对应评论原文。
- 报告中明确标注态度比例是模型估算，不是精确投票统计。
- 显示分析使用了多少条评论，以及是否有缺失。
- 提供“在新标签页打开”“下载 HTML”“复制报告链接或路径”等操作。

当前 HTML 报告已经有可展开树、态度条和典型原话，因此不需要立刻引入复杂图形库。先把“可解释性”和“导航”做好，比直接做横向可缩放树更有价值。

### P1：移动窄屏布局需要单独设计

当前 `workbench.css` 在 `960px` 以下把左右栏改成单列，但这只是结构折叠，并没有解决长页面问题。

建议在窄屏下改成：

```text
顶部任务摘要
采集/分析进度
报告预览
可折叠的日志
可折叠的设置
```

具体调整：

- 侧边栏不应该永远排在报告前面。
- 日志默认折叠，只展示最后一条状态。
- 报告 iframe 使用稳定的最小高度。
- 设置区域放入抽屉或折叠面板。
- 顶部操作按钮固定或保持可见。
- 标题、URL 和作者信息允许换行，不要横向溢出。
- 目录名称和错误文本需要截断并提供完整悬浮提示。

### P1：明确区分“数据状态”和“任务状态”

这是非常容易被忽略但很关键的一点。

建议分别显示两个状态：

```text
任务状态：正在采集 / 分析失败 / 已完成
数据状态：完整 / 部分完整 / 未知
```

例如：

```text
任务状态：分析完成
数据状态：部分完整，2 条楼中楼获取失败
```

不要只显示绿色的“完成”，否则用户会误以为报告基于完整数据。

### P2：保留现有风格，但统一视觉语言

当前工作台是深色的青绿色工具站风格，报告 HTML 是浅色纸张风格，Content Script 面板又使用 Ant Design 和蓝色按钮。三处并不冲突，但品牌感比较分散。

建议不是全部改成一个颜色，而是统一几个基础规则：

- 工作台：深色，强调任务状态和过程。
- 报告：浅色，强调阅读和引用。
- 知乎页面浮动面板：轻量、低干扰，只负责发起操作。
- 统一主色、错误色、警告色和成功色的语义。
- “生成报告”“重新分析”“下载报告”等主要操作使用一致的按钮层级。
- 把“生成报告（工作台）”“下载 ZIP”“保存到文件夹”明确区分为不同类型操作。
- “重新生成”改成更准确的名称，例如“重新采集并分析”。
- 需要重试时使用“仅重新分析”或“重试失败评论”，不要继续使用笼统的“重新生成”。

**三、我建议的实施顺序**

第一阶段，优先修数据和失败恢复：

1. 重做 bundle 完整性字段。
2. 区分一级评论数、总节点数和楼中楼失败数。
3. 保存部分采集结果。
4. 支持仅重新分析已有 bundle。
5. 为模型输出增加结构校验。
6. 让任务状态可恢复。

第二阶段，完善工作台：

1. 增加任务历史。
2. 增加 API 测试和目录权限检查。
3. 给 403、权限失效、API 失败、模型 JSON 错误提供对应按钮。
4. 显示可解释的采集指标。
5. 把提示词编辑移到设置抽屉。
6. 重新设计移动端单列布局。

第三阶段，再提升报告：

1. 报告目录和锚点导航。
2. 议题树筛选和搜索。
3. `quote_id` 跳转到评论原文。
4. 报告元数据和分析置信度。
5. 统一扩展和 Python 的分析结果结构。
6. 增加批量导出、批量分析。

暂时不建议优先做：

- 公网“粘贴链接即分析”。
- 复杂横向图谱和缩放画布。
- 多 Agent 分析。
- 商店版自动发布。
- 大规模多 URL 并发。

这些功能会扩大权限、登录态、限流和数据管理问题，但无法解决当前最核心的“数据是否完整、失败能否恢复、报告是否可信”。

如果只允许先做一刀，我会选：

> 为扩展工作台增加“保存部分 bundle + 仅重新分析已有 bundle + 完整性状态展示”。

这一刀同时解决采集可靠性、模型调试效率、用户等待成本和报告可信度，是当前投入产出比最高的改动。
